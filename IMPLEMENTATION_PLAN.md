# План реалізації тестового для mono

Робочий план після рев’ю. Ціль — показати, як PDF виписки з ЄДР стає звітом з доказами, маршрутом і дією працівника, та здати відтворюваний код і коротке memo. Вимоги — у [бізнес-описі](BUSINESS_LOGIC.md).

Цільовий репозиторій — [projectM](https://github.com/aranel1994-collab/projectM). На момент перевірки в ньому ще немає комітів. Для першого прогону беремо фактичний формат виписки з одного зразка. Ще два використовуємо для перевірки варіативності й оцінки. Інтерфейс, звіт, README, memo і демо готуємо українською.

Стан демо: реалізовано локальний режим і режим відтворення, вебінтерфейс, синтетичні сценарії та оцінку трьох оригіналів. Живий виклик потребує ключа API. Усі оригінали виявилися з текстовим шаром, тому гілку сканів перевірено на синтетичних PDF.

## 1. Зразки, розмітка і правила

- [x] **1.1** Знайти три справжні виписки ТОВ. Бажано дві текстові з різними макетами й один скан або змішаний PDF.
- [x] **1.2** Визначити тип за заголовком, взяти один формат для першого прогону й виписати наявні поля. Окремо перевірити, чи є розділи власників і КБВ.
- [x] **1.3** Розмітити вручну назву, код, місцезнаходження, дату та номер реєстраційного запису, дату формування, орган управління або керівника, власників і КБВ. Записати сторінку та стан, якщо даних немає.
- [x] **1.4** Визначити, які зразки підуть на налаштування і які залишаться для контрольного прогону. Якщо доведеться налаштовуватися на всіх, позначити це в результатах.
- [x] **1.5** Додати ігнорування приватних PDF, ручної розмітки, локальних результатів та ключів ще до першого коміту з даними. Для зовнішньої моделі підготувати знеособлені версії, якщо обробку оригіналів не погоджено.
- [x] **1.6** Створити перший синтетичний PDF за підтвердженим макетом із вигаданими реквізитами. Окремо записати очікувані поля, статуси і маршрут до першого прогону.
- [x] **1.7** Звірити реалізовані рядки матриці з редакціями офіційних джерел. Позначити технічні правила й правила демо-політики окремими підставами.
- [x] **1.8** Підготувати локальний запуск і конфігурацію моделі через змінні середовища. Якщо з’явиться попередній прототип, звірити його з узгодженим обсягом перед інтеграцією.

**Готово**, коли є підтверджений шаблон і перший синтетичний PDF з очікуваними полями та маршрутом. Один зразок достатній для старту наступного етапу.

## 2. Перший звіт із текстового PDF

- [x] **2.1** Приймати PDF і повертати окремі повідомлення для пошкодженого, захищеного та непідтримуваного файла.
- [x] **2.2** Читати PDF по сторінках і визначати, які сторінки мають придатний текст, а які треба читати як зображення.
- [x] **2.3** Додати закриту схему відповіді LLM. Поля передбачають `null`, а коди і номери записів зберігаються рядками.
- [x] **2.4** Додати `live` для виклику моделі й `replay` для зафіксованих відповідей на конкретні PDF. Повернути технічну причину, якщо відповідь не відповідає схемі після повтору.
- [x] **2.5** Перевіряти фрагмент на зазначеній сторінці та його прив’язку до поля або ролі. Зберігати стан непідтвердженого значення окремо.
- [x] **2.6** Додати файловий реєстр правил з ID, редакцією підстави, версією, датою чинності, умовами застосовності й описом наступної дії.
- [x] **2.7** Обчислювати статуси правил і маршрут кодом. Відкриті дії щодо ЄДР, КБВ, санкцій і PEP показувати окремо. Перевірити поведінку за відсутності придатної версії.
- [x] **2.8** Вивести перший звіт із полями, причинами, доказами, відкритими діями, датою, версією правил, моделлю, версіями промпту та схеми і режимом запуску.
- [ ] **2.9** Прогнати один синтетичний PDF від початку до звіту живим викликом. Зафіксувати записаний прогін для регресії.

**Готово**, коли текстовий PDF дає повний звіт і для кожного результату можна відкрити доказ або побачити причину його відсутності.

## 3. Ручна перевірка, ескалація і скани

- [x] **3.1** Звірити необов’язковий заявлений ЄДРПОУ з PDF. Перевірити збіг, розбіжність і сценарій без заявленого коду.
- [x] **3.2** Перевірити документ, у якому код засновника легко переплутати з кодом компанії. Такий доказ не має дати `PASS`.
- [x] **3.3** Додати суперечність між двома кодами, явно наведеними як код самої компанії. Звіт про ескалацію містить обидва докази.
- [x] **3.4** Перевірити порожнє поле КБВ, явну відмітку про відсутність відомостей, відсутній розділ і відмінність від `NOT_APPLICABLE`.
- [x] **3.5** Додати непідтримуваний шаблон або форму юрособи. Показати доступні дані й причину ручного маршруту.
- [x] **3.6** Додати один прохід LLM для сторінок-зображень. Для скану і змішаного PDF з критичним полем на зображенні показати сторінку і `SCAN_SOURCE`.
- [x] **3.7** Додати синтетичний документ із текстом, який намагається вплинути на агента. Перевірити, що результат правил визначається доказами та кодом.
- [x] **3.8** Реалізувати коротке LLM-пояснення для `REVIEW` і `FAIL` і показувати текст з правила у разі збою. Перевірити незмінність маршруту й дії.

**Готово**, коли є синтетичні приклади всіх трьох маршрутів і окремі регресії для хибного `PASS`, скану та збою пояснення.

## 4. Вебдемо і дія працівника

- [x] **4.1** Зробити одну сторінку із завантаженням PDF і необов’язковим полем заявленого коду.
- [x] **4.2** Поставити звіт поруч із PDF. Відкривати сторінку з доказом за кліком і підсвічувати однозначний збіг фрагмента.
- [x] **4.3** Показати маршрут, причини, відкриті дії та режим запуску українськими підписами.
- [x] **4.4** Додати одну дію щодо поточного запуску: «Передати далі», «Запросити документ» або «Ескалація», з полем коментаря.
- [x] **4.5** Пройти три основні сценарії в браузері. Перевірити завантаження нового PDF як окремого прогону.

**Готово**, коли рев’юер може завантажити PDF, відкрити доказ і зафіксувати дію на одній сторінці. Повторні запуски в тому самому кейсі, черга, аудит і погодження змін правил описуються в memo.

**Готово**, коли демо працює зі свіжої копії, звіт показує докази та подальші дії, а memo містить виміряні результати і план продакшну.
